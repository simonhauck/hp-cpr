# Release-gated GitHub Pages with batched, manual releases

The web app is published from a single GitHub Pages site at `https://simonhauck.github.io/hp-cpr/`, but only from a tagged release, not from `main`. GitHub Pages allows one site per repository and every deployment replaces the whole site, so a separate dev site would either need a second repository or reintroduce a race between two deployments. We chose one site serving the latest release: web users get the same batched, manually approved build as the APK and later the Play Store artifact, while `main` stays a development state whose builds are available as workflow artifacts.

Releases are cut by release-please from Conventional Commits. It keeps one release PR open until we merge it, which batches several features and fixes into one version instead of releasing every merge. The generated release PR does not run CI, because release-please uses `GITHUB_TOKEN` and GitHub suppresses workflow runs for resources it creates. That is deliberate: the release PR only bumps `pubspec.yaml` and `CHANGELOG.md`; the delivery workflow checks the merged commit before it tags, deploys, or attaches artifacts. Using a PAT or GitHub App would make the release PR show checks, at the cost of a long-lived write token.

Direct pushes to `main` are allowed for the solo workflow. GitHub cannot require status checks before a direct push, so the checks gate the release and Pages deployment instead: a red `main` cannot produce a tag or update the site. A separate ruleset blocks force pushes and deletions without a bypass. The trade-off is that a broken main commit can exist until it is fixed, but it never reaches users.

**Considered options:** a second repository with a dev site (independent deploys, but two Pages sites, shared `github.io` browser storage, and cross-repo tokens); one site serving `main` (simpler, but every merge reaches web users and the release gate only protects the APK); auto-merging the release PR (no human gate); and a PAT or GitHub App for checked release PRs (more setup and a long-lived secret).

**Consequences:** the live page lags `main` by at least one release cycle; testers use the main APK artifact for unreleased work. The APK is release-mode but debug-signed and is not a Play Store artifact. The `+build` number is bumped by release-please, so the later Play upload can use it as `versionCode` without reworking versioning.
